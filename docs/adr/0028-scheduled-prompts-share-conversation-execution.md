# Scheduled prompts share Conversation execution without becoming user Evidence

A prompt Scheduled trigger targets one Conversation, runs through that Conversation's warm pi runtime, uses its Conversation prompt, and serializes with its interactive turns. This preserves scoped working context and one ordered transcript per Conversation, refining ADR-0002's earlier example of scheduled work using an ephemeral task process and extending ADR-0023's host-owned Conversation semantics.

Each firing first creates an immutable Scheduled occurrence snapshot containing trigger version, intended firing time, action, payload, target Conversation, and model profile. A prompt occurrence links exactly one scheduled Conversation turn whose Provenance identifies the Scheduled trigger and intended firing time. Its Scheduled Message and response remain visible, but the Scheduled Message is context rather than fresh user Evidence. Because pi RPC accepts prompts only as user-role input, Tether sends a host-owned Scheduled-context wrapper while keeping canonical content unchanged. Scheduled execution cannot authorize Product observation capture, email-to-Evidence promotion, or another capability requiring fresh active-turn user Evidence, and it never emits voice cues or speech. Recurring-trigger edits affect later occurrences only; a one-off with a pending or running occurrence cannot be edited. Deleting a trigger cancels pending occurrences and turns, not accepted execution. Traces retain the Conversation turn ID and `scheduled` origin, while pi session ID remains operational metadata. Cancellation targets one Conversation turn, and fixed-message triggers remain outside the Conversation.

A deep Conversation-turn module exposes four operations: submit a request with a typed `ChatFrameSink`, wait for terminal settlement without owning execution, cancel a turn or pending occurrence, and reconcile durable state. Browser and silent adapters serialize or discard typed frames; disconnecting an adapter never cancels execution. Conversation turns use one durable lifecycle: pending, running after pi accepts the prompt, succeeded, failed, or cancelled. Interactive submission is idempotent by a browser-generated request ID, while scheduled submission is idempotent by occurrence identity. Turns snapshot the concrete provider, model, thinking configuration, and scope revision, and retain partial reasoning and tool Messages when execution fails. Scheduled failures render as retrying or failed state on the Scheduled Message rather than as manufactured assistant output. The Scheduled trigger surface shows the target Conversation, pinned profile, next firing, latest occurrence outcome, and linked Conversation turn.

Only explicitly classified transient failures before pi accepts the prompt retry automatically, with at most two quick retries; permanent, unknown, and exhausted failures default to terminal. Prompt-occurrence agent failures do not enter the scheduler's broad dispatch retry loop: a failed one-off becomes failed and a failed recurring occurrence advances, while fixed-message delivery retains bounded dispatch retries. A failure or interruption after acceptance is terminal for that occurrence because tools may already have produced side effects. Restart reconciliation settles succeeded turns without rerunning, dispatches pending turns, marks interrupted running turns failed, and creates a turn only when a prompt occurrence has none. Conversation-turn success advances recurrence independently of Web Push. Push delivery retries separately from the stored assistant Message and never changes or reruns the turn. Graceful shutdown briefly drains running work, fails unresolved accepted turns, and leaves pending turns for safe startup reconciliation. Scheduled dispatch rejects an archived target without running pi, and successful push delivery identifies and deep-links the target Conversation. Existing transcript rows are grouped from each user Message through the row before the next user Message; leading non-user rows form one historical group. Groups containing assistant output are backfilled as succeeded and incomplete groups as failed, without guessing which historical user Messages came from Scheduled triggers or changing their Evidence semantics.
